## A. Decisions (ruled; cite, don't re-litigate)

**D1 — The seam: no new verb, one service, three phases.** `perform_agent_create` is the placement authority; `harness agent create` and `runtime.agent.create` are its two doors and stay byte-parallel; `persona instance create --add-instance` stays the roster-only recovery door and is not touched. The service gains a pure `layout` step before any write (D2) and a `skills` phase after `placement` (D5). **Why:** UC-H1/H3 already hoisted the sequence out of the RPC handler precisely so a lane switch is never a behaviour change; a second verb (`agent place`) would be the parallel authority the master prompt forbids. **The authority question, answered as two questions:** the persona-instance row answers "does this agent exist" (the roster-only door legitimately mints rows with no placement); the instance-keyed office actor answers "is it on this level"; the reservation receipt is the join for one gesture. "Placed" ≡ a live actor whose `persona_instance_id` names a live row. A row without an actor is `unplaced` (legal); an actor whose instance is retired or missing is an `orphan_actor` (defect). Neither store is folded into the other; the join gets a read-only census (`harness doctor` → `placement_census`, D8) rather than a merge.

**D2 — Auto-layout: hermes owns the policy; the launcher keeps a fixture-pinned prediction.** New pure module `agent_runtime/office_layout_policy.py` — `next_free_slot(occupied: Iterable[tuple[float,float]], *, lane_offset=(0,0)) -> tuple[float,float]` and `occupied_positions(actors, *, folder)` — with the SAME constants and scan order as the launcher's `MissionOfficePlacementPolicy` (F10), and one shared case fixture committed byte-identical in both repos (`tests/fixtures/office_layout/cases.json` ↔ launcher `test/fixtures/harness_office_layout/cases.json`, `MANIFEST.sha256` on both sides, the `harness_stream` pattern). `position` becomes OPTIONAL on `runtime.agent.create` and `--pos` optional on `agent create`: present → operator data, verbatim, exactly as today; absent → the policy over the workspace's live actors in the request's folder. The ack gains `position: [x, y]` and `actor: <the row as stored>` — additive on an existing ack, no manifest integer move; the launcher adopts the SERVER's actor (this is what discharges [office-gesture-prediction-remainder](office-gesture-prediction-remainder.md) Row 2's "adoption trusts the client's key"). **Why hermes:** two policies that can disagree are the defect this plan exists for; a policy on the server is the one every door shares, and a fixture pin is how this codebase already keeps two repos byte-equal. **Why the launcher keeps a copy:** the pending chip and the staged node need a world position before the ack, and the prediction is cheap to pin.

**D3 — Notification: no surface-revision bump; the existing `office_actor` create patch is the frame; S0 proves it live.** Ruled against bumping `surface.revision` on actor writes (F5). The frame a client consumes is the `patch` batch carrying `{entity: office_actor, op: upsert, created: true}` and `{entity: persona_instance, op: upsert, created: true}` from one create; the consumer is `MissionReadModel._applyOfficeActorPatch` + the generic `persona_instance` fold. A client that declares no folds receives the demoted full core (correct, costlier); a client not connected hydrates on reconnect. Both degrade to "stale until refresh", never to a wrong render, because the scene is derived from snapshot truth, not from a revision counter. **What the plan adds:** the live proof and a byte-pinned golden of the two-patch batch in both fixture dirs (S0). If S0 shows a demote or a drop, its reason is the first slice's finding and everything downstream waits on it.

**D4 — Idempotence and failure: keep the reservation; add a resumable `skills` phase; never roll back a placed agent for a skill fault.** Reservation states become `instance_minted → placed → done | rolled_back`. **Migration rule, exact:** `agent_create_reservations._VALID_STATES` gains `STATE_PLACED = "placed"`; a receipt read back as `done` with NO `skills` field is a pre-plan receipt and is treated as `done` (never re-entered); a `placed` receipt carries `skills: [...]` (the normalized request list, possibly empty) and resumes at the skills phase only; an unknown state stays `reservation_corrupt` exactly as today. The `done` literal is not renamed — an old serve reading a new receipt sees `placed` as corrupt and refuses loudly rather than re-minting, which is the safe direction. A `skills`-phase refusal returns `phase: "skills"`, `rolled_back: false`, `next_expected` carrying the retry sentence, and the receipt retains the requested skill list; **the key is `next_expected`, not `resume`** — this paragraph said `resume:` and the shipped code has always written `next_expected` (`agent_create._SKILLS_RETRY_SENTENCE`, rendered at the single site `_skills_refusal`), which is also the spelling D11's refusal `data` block names, so the plan disagreed with both the code and itself (corrected S4b); a retry with the same key re-enters at `skills` without re-minting or re-placing. **Why:** a placed agent without its skills is exactly what every launcher drop is today — a valid, messageable state; retiring it to satisfy atomicity would archive a working agent to undo a file copy. Placement-phase compensation stays as it is (retire = archive). The unstamped `AgentCreateInvalid` arms (F3) get `rolled_back: True` in the same slice.

**D5 — Skills: the verb assigns AND installs, at the instance tier, behind two new gates.** The parameter is `skills: ["<id>", …]` on `runtime.agent.create` and `--skill <id>` (repeatable) on the CLI — the two doors stay byte-parallel (UC-H3's rule), and a remote connector, which can never run the install's CLI, gets the whole verb over `call`. Ids are validated with `safe_id` and resolved by name through `resolve_skills` — never path-joined from input, so a traversal-shaped id is `skill_unresolved`, not a filesystem read. The install step runs on the INSTALL's machine into ITS shared root (`install_harness_skill`'s staged `copytree` + atomic `os.replace`, no lock needed: two concurrent creates installing one skill race to an identical replace); the `skill_overrides` write takes the persona-instance store's own lock as `update_profile` does today. `skills` writes `skill_overrides` on the NEW instance through `PersonaInstanceStore.update_profile(skills=[…])` — never `persona.skills` (a persona-tier write would silently reconfigure every other instance of that persona, and no operator verb has ever done that). Absent `--skill` leaves `skill_overrides = None` (inherit). Before assignment: (a) every id must resolve `status == "resolved"` under `agent/skill_utils.resolve_skills` or the phase refuses `skill_unresolved` naming the id and its status (`missing | collision | invalid_source`); (b) every CANONICAL id (`CANONICAL_SHARED_SKILL_IDS`) is passed through `install_harness_skill` first, and after install `harness_skill_hash_mismatches([...])` must be empty or the phase refuses `skill_install_diverged` with both hashes. **The one hazard this plan inherits, recorded here so neither plan is surprised.** `patch_coverage.accepted_fold_entities` takes the INTERSECTION across every subscriber in the room, on both lanes (canon 03 §4). The gateway's Stage 5 mobile fold profile is deliberately narrow — the office canvas is out of scope on a phone — so the moment a phone subscribes, the room's accepted set loses `office_actor`/`office_actor_lifecycle`, and every placement's batch DEMOTES to a ~1 MB full core for the desktop too. D3's guarantee ("clients notice") still holds — a full core is correct, never wrong — but the cost model the drop latency tables assume (hermes 06) does not. This is the gateway plan's R10 in a new light: the fix is **per-subscriber promotion at the hub** (fan the patch to declaring subscribers and the demoted core to the others) rather than one room-wide set — a hub change, not a placement change. Filed as a row for the gateway plan (its §5 R10 bullet gains this consequence); S0 here adds a second golden — the same create observed by a narrow-profile subscriber — so the demote path is pinned as well as the fold path, and nobody discovers it on a phone.

**What the gateway must NOT assume from this plan:** that `harness agent create` is reachable remotely (it is not — the argv op lane carries capabilities the launcher lowers, and a remote connector should call the RPC, never lower the CLI), or that `placement_census` (a `harness doctor` report, S6) is a method — it is a CLI/ops-lane report until someone needs it over `call`.

- **Two policies, one fixture.** The fixture pin proves equality on the cases in the file, not on every floor. - **The desk fence meets pulled data.** A workspace pulled from a realm can already hold two desks for one persona; the fence refuses the NEXT write, not the existing state. The render-time `duplicate_desk` warning stays for exactly that, and `harness office actor-upsert` on such a workspace will refuse a desk move until one is archived — a refusal with the holder named, not a silent write.

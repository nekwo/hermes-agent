## 1. The rows, and what the tree actually said

### Row 1 — the shim execs itself. TRUE, and worse than filed.

`_resolve_hermes_exe` took its directory from
`tools.environments.local._resolve_hermes_bin_dir()`, whose first rung is
`shutil.which("hermes")`. The shim is written into a directory this module then
puts ON PATH, so from the second `postinstall` onward `which` answers with the
shim and `render_posix_shim` emits `exec "<shim>"` into `<shim>`.

Two things the row did not say, both found by running it:

* **The loop is reachable with no resolution bug at all.** A
  `pip install --user` puts the genuine console-script at `~/.local/bin/hermes`
  — which *is* the POSIX shim path. Ordering alone cannot fix that case;
  nothing stands behind the shim there, and the only honest answer is to
  refuse. That is why the fix is two halves and not one.
* **`shutil.which` can answer RELATIVELY.** On Windows it searches the current
  directory before PATH, and this repo's root holds a `hermes` script, so
  inside the suite `shutil.which("hermes")` returns `.\hermes`. The pre-fix
  chain would have taken `.` as the install dir and baked a relative exec
  target into the shim — a different broken command in every directory the
  operator stands in. Found because a red-first revert of the ordering
  *passed*: the PATH rung was answering `.\hermes` and being discarded, so the
  ordering revert had nothing to change. Third fence added (`os.path.isabs`),
  with its own claim and its own test.

`tools/environments/local.py` is deliberately NOT touched. Its PATH-first order
is right for its own purpose — it prepends the install dir onto a *subshell's*
PATH so a plugin shelling out to bare `hermes` resolves, and there the shim on
PATH IS the correct answer. The shim writer wants the thing standing *behind*
the shim. Both orders now say so in their own docstring.

### Row 2 — a TEST's `HERMES_HOME` in the operator's shim. Half true; the other half is the real hole.

The production derivation was already right: `cmd_postinstall` passes
`get_hermes_home()`, the canonical resolution for the profile being installed.
No caller passes a scratch path.

The hole is on the test side, and it is an *absence*: `_hermetic_environment`
redirects `HERMES_HOME` and, by an explicit ruling recorded in that fixture,
does NOT redirect `HOME`. The shim's install directory is HOME-anchored
(`~/.local/bin`; `%LOCALAPPDATA%/hermes/bin` on Windows), so it stayed REAL for
every test in the tree. Anything reaching postinstall wrote a genuine shim onto
the developer's PATH with the test's temp `HERMES_HOME` baked in — a durable
file pointing at a directory that is deleted at teardown.

Reproduced, with the install dir pointed at a scratch stand-in so nothing real
was touched (see §3, proof 4). The escaped file:

```
@echo off
rem Hermes Agent command shim - generated by `hermes postinstall`.
if not defined HERMES_HOME set "HERMES_HOME=…\pytest-6048\test_postinstall_writes_its_sh-0\hermes_test"
"…\pytest-6048\test_postinstall_writes_its_sh-0\venv\Scripts\hermes.exe" %*
```

That is the operator's Mac artifact exactly.

Fix: the derivation moves into `path_setup._shim_install_dir()` — one seam —
and `tests/conftest.py` grows an autouse `_isolate_hermes_shim_dir` that pins
it to `tmp_path`. Redirecting the seam rather than `HOME` keeps the standing
ruling intact; making it autouse rather than per-test is deliberate, because
the tests that already remembered to isolate are not the population this
protects.

**Standing gap, not closed here:** a monkeypatch reaches in-process code only.
A test (or launcher E2E) that spawns `hermes postinstall` as a SUBPROCESS is
still free to write a real shim, and that subprocess route is the likelier
source of the operator's Mac file — `scripts/install-mission-control-hermes.ps1`
runs `hermes postinstall --yes --json` for real. Isolating that needs the
child's `HOME`/`LOCALAPPDATA` set by whoever spawns it. Filed as a row.

### Row 3 — `backfill-home`'s skipped arm loses the directory. TRUE.

`_cmd_characters_backfill_home` built `{"id", "directory"}` for every row and
then printed the directory on the stamped arm only. The skipped arm is the one
that needs it most: the population is drafts that already carry a home, and a
copied draft keeps the id inside its own `draft.json` AND the home it was made
in — so an id-collision prints two skipped rows differing in nothing but the
directory. The verb's own docstring already stated the rule ("The receipt names
directories beside ids"); one of its two arms did not implement it.

**The sibling verb, checked as asked.** `_cmd_characters_migrate_home`'s
skipped line (`  skipped {kind} {id-or-slug}  {reason}`) has the SAME shape of
asymmetry but is mitigated, unevenly:

* rows from `_relocate` carry `{kind, id}` + a `reason` — the collision reason
  embeds the *destination* path, and `could not move: <exc>` usually names a
  path, but the SOURCE directory is never on the line;
* the "not an installed character" skip does carry `directory` in the payload,
  and still does not print it.

Its moved/stamped lines do name directories, and its comment claims "Every line
names the DIRECTORY beside the id or slug" — which its skipped arm does not
honour. Not fixed here (the row scoped this to a check), and filed: the fix
needs `directory` added to the `_relocate` row dicts in
`agent/charsheet/draft.py` as well as the print, i.e. a production change in a
second file with its own claim.

## 6. What the tree-wide fixture costs, measured rather than assumed

`_isolate_hermes_shim_dir` is autouse across the whole tree, so it imports
`hermes_cli.path_setup` for every test in the repo. Measured on this box:

```

hermes_cli.config dragged in: False
```

That matters because `tests/hermes_cli/test_tirith_config.py::TestImportWeight`
puts a number on the alternative: `hermes_cli.config` costs >100 transitive
modules. `path_setup` imports `os`, `shutil`, `stat`, `sys`, `dataclasses` and
`pathlib` and nothing of ours, so the fixture is cheap enough to be autouse.

enumerated and are unaffected — the only one about our own modules
(`"hermes_cli.config" not in sys.modules`) runs inside a subprocess probe, and
the fixture does not pull that module in anyway.
